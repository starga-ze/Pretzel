External App Launch reproduces google-chrome: / com-okta-authenticator: style scheme navigation

Navigates to a non-http(s) scheme so the browser enters its external-protocol handling path (the step a secure browser logs as an external application launch). Pick how the navigation is started — a real click, a script with no user gesture, a hidden iframe, or a repeating burst — and watch the activity log.

A remembered “always allow” is stored per (origin, scheme), so only a new scheme escapes it — but a scheme no app registered can never raise a dialog. A path token keeps a scheme that really has a handler while still making each event distinct.

Navigation target google-chrome:

Which app opens is the OS's decision, not this page's. The page only picks the scheme string; the desktop's scheme-handler registration picks the binary. google-chrome: is registered by Google Chrome on a normal desktop, so it opens Chrome. To make a secure browser answer instead, either navigate to the scheme it registers (Scan schemes tries candidates and reports which one reacts), or repoint the registration for x-scheme-handler/google-chrome at it — Linux: xdg-mime default <app>.desktop x-scheme-handler/google-chrome; Windows: the HKCU\Software\Classes\google-chrome\shell\open\command key; macOS: the app's CFBundleURLSchemes plus a default-handler reset. Pick pretzel-lab-noapp: to generate the launch attempt with no app at all — that is the "External Application: None" case.

A browser-generated block (“Not allowed to launch … because a user gesture is required”, “… scheme does not have a registered handler”) is written to the DevTools console by the browser itself and cannot be caught from page script — the log below only records what this page attempted. Open DevTools to see the browser's own verdict next to it.
